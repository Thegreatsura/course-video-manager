# Background work runs in the Sidecar: the tab only enqueues and listens

A background job is work the author starts and walks away from: an export, a vertical Short, a post, a Course **Autofill**, a **Publish**, a Clip's transcription. Until this change each one was a single HTTP request, usually a server-sent event stream, and a browser queue (the Upload Manager) kept it alive. Closing or reloading the tab aborted the request, and the server interrupted the work. The job's state lived only in React memory, so nothing ran it again, and its failure was a toast that no log kept. [ADR 0024](0024-autofill-is-a-job-of-its-own.md) accepted that for the Autofill and named "a durable background worker" as the deferred next step. This ADR records that step. The full migration, batch by batch, is in `docs/plans/background-jobs-sidecar.md`.

## Decision

1. **Every background job is a Job, and the Sidecar runs it.** A Job is a row in `job`, and its history is the `job_event` rows, in the same Postgres as the data (`packages/core/db/schema-jobs.ts`). The browser (through `POST /api/jobs`, `routes/api.jobs.ts`) and `cvm course publish` start one with `enqueueJob` (`apps/local/sidecar/job-specs.ts`), checked against `JOB_KIND_SPECS`. A running Job starts another only through `ctx.enqueue` (`sidecar/job-context.test.ts`). The **Sidecar** (`apps/local/sidecar/`) claims each Job, runs its kind's handler (`sidecar/kinds/`), logs it to `.data/logs/jobs/<job id>.jsonl`, and writes its **Job Events**. Every background job is a kind: `export`, `batch-export`, `render-vertical`, `youtube`, `youtube-shorts`, `buffer`, `ai-hero`, `skills-changelog`, `autofill`, `publish` and `transcribe-clips`.
2. **The tab only enqueues and listens, over one Job Event stream.** Each tab opens one `EventSource` on `GET /api/jobs/events` (`features/jobs/use-jobs.ts`). The app passes through the Sidecar's feed (`sidecar/job-event-feed.ts`): a snapshot of recent Jobs, then every new Job Event. The jobs reducer (`features/jobs/jobs-reducer.ts`) folds them into the rows the Upload Manager draws, and `job-event-hub.ts` hands the same stream to the video editor for Clip transcription. Closing the stream cancels nothing. The browser Upload Manager's own queue, reducer and retry path are deleted (#1930). `features/upload-manager/` now only draws Job rows and their ETA.
3. **Retries are copied, not invented** (Matt's decision 2). Each kind's attempts come from what the browser allowed, and are listed in `UPLOAD_MANAGER_POLICIES` and `CLIP_TRANSCRIPTION_POLICY` (`sidecar/retry-policy.ts`): an export and a vertical render get 3 attempts; a Batch export, an Autofill and a Clip transcription get 1. A Batch export Video that fails is handed on as its own `export` Job with 2 attempts, so it still runs at most 3 + 2 = 5 times. The rule lives once, in `packages/core/services/db-job-operations.server.ts`. A failed attempt goes straight back to the queue while attempts remain. A run the Sidecar lost (it died, or the Job's lease ran out) counts as a failed attempt (`recoverExpiredJobs`). A deliberate stop (a signal) puts the Job back at the same attempt (`returnJobToQueue`). When a Job fails for good, every Job waiting on it fails too (`failDependents`). The narrow retries inside a service (Dropbox HTTP, an export inside a Publish, Autofill's rate limit) stay where they were.
4. **Two lanes, both copied** (Matt's decision 3). `sidecar/lanes.ts` has a `default` lane with no limit, as the Upload Manager had none, and a `publish` lane that runs one Job at a time. The `publish` lane replaces the Publish's one-permit `courseVersionMutationSemaphore`. Limits on a resource inside a Job stay in the service: ffmpeg's permits, 6 exports at a time, Autofill's 6 Videos, Dropbox's upload pool and Whisper's 20.
5. **A post and a Publish never run again on their own.** Matt: "I definitely don't want reruns to happen on their own. Posting twice would be disastrous."
   - **Posts.** A posting kind (YouTube upload, YouTube Shorts, Buffer, AI Hero, Skills Changelog) is defined with `definePostingJobKind` (`sidecar/job-kind.ts`). It always gets `POSTING_JOB_POLICY`: exactly 1 attempt. No failure, stop or crash runs it again. A post that is cut off ends `interrupted`. The Sidecar then checks the service, read-only, to see whether the post went out (`sidecar/post-checks.ts`). Only the author's **Retry** runs a post again (`retryJob`, `POST /api/jobs/<id>/retry`). The server refuses a Retry when the run went out, when the author is retrying an older run, or when the Job it waits on did not succeed (`packages/core/services/db-job-posting.server.ts`).
   - **Publish.** A `publish` Job has 1 attempt and `neverRequeued` (`retry-policy.ts`). A stop or a crash ends it `interrupted`. If it got past **Submit**, its **Pending Version** waits on the publish page, where the author chooses **Promote** or **Discard** by hand (`features/publish/pending-recovery-banner.tsx`). `retryJob` refuses every kind that is not a post, so a Publish has no Retry. A new Publish is a new Job.
   - **Enforcement.** `isNeverReRun` (`job-kind.ts`) holds both cases in the Sidecar's settle and recovery code (`sidecar/sidecar.ts`). `sidecar/posting-kinds.test.ts` and `sidecar/publish-kind.test.ts` fail if either slips back.
6. **Spawning is the Sidecar's.** Everything that starts a process for background work is in the Sidecar's own layer (`sidecar/sidecar-layer.ts`), not the app server's `layerLive`. That covers the encodes, the Overlay renderer, the vertical render, Publish and Whisper (`WhisperTranscriptionService`). The code that does this work asks for `SidecarContext` (`app/services/sidecar-context.ts`), and only the Sidecar's layer provides it, so a route that reaches it does not compile. Three guards hold the rest:
   - `apps/local/.dependency-cruiser.spawn.cjs` (run by `lint:boundaries`) refuses any path from `app/routes/` to a Sidecar spawner, the Sidecar's layer or a Job handler.
   - `scripts/check-background-jobs.ts` counts streaming routes, browser drivers and `Command.make` calls against a shrink-only allowlist, `scripts/background-jobs-allowlist.json`, with a reason for each file.
   - `pnpm run check` runs both.
7. **What stays in the browser, by name.** The allowlist holds only work that a person watches, never work the author walks away from:
   - the chapter Autofill modal and its stream (`autofill-chapters-modal.tsx`, `api.videos.$videoId.autofill-chapters.ts`), because it is a conversation with the person watching;
   - OBS clip ingestion (#13, the loop in `features/video-editor/edit-effect-handlers.ts`) and the wait for OBS's virtual camera (`obs-connector.tsx`), because both belong to a live **Recording Session**;
   - the app server's quick `ffmpeg`/`ffprobe` calls (`ffmpeg-commands.ts`, `video-processing-service.ts`), because a person waits on each for a moment.

   `cvm footage transcribe` runs on the author's machine (`footage-transcription.ts`). The interactive AI streams (the Article Writer, completions) are conversations too, and stay.

## What the tab still decides

- **Toasts are reducer decisions carried on effects.** When a Job settles, the jobs reducer builds the toast (`features/jobs/job-succeeded-toast.ts`) and puts it on the `show-job-succeeded-toast` effect. The handler only draws it, and never reads state (#1926).
- **A toast fires only for a settlement this tab heard live.** When the feed gets its first subscriber, it re-sends the last 60 seconds of events. A Job Event at or below the snapshot's cursor updates the row but never toasts (`jobs-reducer.ts`, `caughtUp`, #1938). So a new tab does not re-announce an export that finished, or was dismissed, before it opened.
- **Clip transcription never toasts and draws no row.** The Clip shows its own state. The editor's clip reducer folds the `transcribe-clips` Job's `clips-started` and `clip-settled` events (`features/video-editor/clip-state-reducer-transcription-jobs.ts`).
- **The ETA comes from Job Event timestamps.** A row's stage durations and rates come from each event's `at`, so a reopened tab replays the same countdown. Stage history is read from `job_event`, not localStorage: `GET /api/jobs/stage-history` returns the newest 20 succeeded Jobs of each kind (`packages/core/services/db-job-stage-history.server.ts`). A fresh browser therefore has an ETA from its first export (#1933, #1938).

## Considered and rejected

- **A per-checkout SQLite job table.** It would isolate every checkout for free. But Jobs could not join to the Videos and Courses they work on, `cvm` could not see them, and the domain would be split across two databases. The job table is in the same Postgres. A verify-cvm clone gets its own table, and the worktree guard (`packages/core/db/connection-guard.ts`) already stops a worktree from writing to production.
- **An `ai` lane** (one Autofill at a time). Nothing held a second Autofill back in the browser, so a lane would have been a new limit. An Autofill runs in the `default` lane, and its 6 Videos at a time stay in the service.
- **Automatic Promote or Discard of an interrupted Publish.** The first plan reconciled a Pending Version on its own after a crash. That would be a new policy for the one Job that can leave the course half-published. The author still decides, from the receipt the publish page shows.
- **Re-running a cut-off post, as the browser did.** The browser retried a failed post up to 3 times, and ran one again after a server death, when the post might already have landed. Copying that exactly was decision 2; decision 5 overrides it for posts. A Publish already had 1 attempt, and `neverRequeued` adds that a stop does not put it back.
- **Re-transcribing Clips stuck in `transcribing`.** Matt's call: the sweep (`sidecar/stuck-clip-sweep.ts`) marks a Clip that no live `transcribe-clips` Job holds as `failed`, and the author re-transcribes it by hand. The sweep never enqueues a Job and never calls Whisper (#1925).

## Consequences

- **Closing the browser never stops a Job.** Reopening a tab shows it from the snapshot, still running or settled.
- **Work waits while the Sidecar is down.** Enqueue still succeeds, because a Job is a row, and every page shows "Background jobs are stopped" (`features/jobs/sidecar-down-banner.tsx`). Jobs start when the Sidecar comes back. `pnpm dev`, `pnpm start` and every verify-cvm run start one.
- **A new kind of background work is a Job kind:** its params in `sidecar/job-params.ts`, a handler under `sidecar/kinds/`, one line in `JOB_KINDS` (`sidecar/job-kinds.ts`) and its spec in `JOB_KIND_SPECS`. A new streaming route, browser loop or spawn in a file the guards scan fails `check`, unless it is added to the allowlist with a reason.
- **A post or a Publish that is cut off needs a person.** That is the price of never posting twice. An interrupted post shows its post-check verdict and a Retry. An interrupted Publish sends the author to the publish page.
- **Supersedes ADR 0024's deferred note.** The Autofill runs as an `autofill` Job (`sidecar/kinds/autofill.ts`) and no longer stops with the tab. The rest of ADR 0024 stands.
